# Dashboard design spec

The spec the dashboard is built to. Change it here first, then the code.

## What it is
A local web page for watching and answering the Claude Code sessions that work one project together: one Coordinator plus any number of lanes (Lane A, Lane B, ...). It replaces following a terminal per session. The lanes are not listed anywhere in advance: each `lane-<id>.md` file in the lanes folder is a lane, so a new lane (Lane D, Lane E) appears by itself, with its own colour, card and `about` chips. Later this may grow more levels (a lane running sub-lanes) and coordinators of different people talking to each other; nothing in the page assumes a fixed count. It is generic: any project that uses the setup in `docs/SETUP.md` can point it at its lanes folder.

## What it reads (never changes)
A lanes folder per project, usually `~/.claude/lanes/<project>/`:
- `plan.md`: queues per lane, shared files, merge order, decisions log.
- `coordinator.md` and one `lane-<id>.md` per lane (`lane-a.md`, `lane-b.md`, ...): one status file per session, rewritten each time. Lane files are `Key: value` lines (`Updated`, `State`, `Now`, `Started`, `ETA`, `Decision`, `Branch`, `Open PRs`, `Files claimed`, `Blocked on`, `Needs from other lanes`, `Done today`, `Handoff`; `Done today` and `Handoff` can run over several lines; see `templates/status-file.md`). The coordinator's file is looser markdown with a `Now:` line.
- `rules.md`, `coordinator-rules.md`: shown read-only, behind the menu.
- `updates.jsonl`: sessions append one JSON object per line (formats in the README).

## What it writes
Only `answers.jsonl` (appended) and new files in `attachments/` in the lanes folder. Nothing in any repo. It never runs `claude` and never messages a session; the coordinator watches `answers.jsonl` and passes lines on.

## Layout
One screen, no page scrolling: the page is the viewport height and each panel scrolls inside itself. At a glance it must be obvious what needs the person. Three columns; under about 1000px they become tabs (Needs you with a count, Chat, Sessions).

**Left (about 300px)**
- **Needs you**, rows in this order, each with a small heading and count ("Urgent · 2") and its own one-card carousel ("1 of 3", the same compact card and modal); a row with no cards is not shown. Urgent: questions and to dos tagged `urgent` or `blocking`, and lane restart cards (title starts "Lane X handed off" or "Restart Lane X"). Decide: the other open questions. Do: to dos that can be done now and are not staging checks. Check on staging: to dos whose title starts with Check, Compare or Try, or with `"check":"staging"`, once they can be done. Waiting: to dos that cannot be done yet, on a grey card with a line saying what they wait for: `after:"merge"` with its `pr` not merged, `"waitsFor":{"pr":N}` until N merges, or `"waitsFor":{"stagingRelease":"<sha7>"}` until the project's `stagingHealthUrl` reports that release (the server reads only its `release` field, once a minute, only while such a card is open). When that clears, the card moves to Do or Check by itself and glows. A card that fits two rows goes to the first of Urgent, Decide, Waiting, Check, Do. The header count leaves Waiting out. Ready to merge stays its own section below. Needs you never folds; it takes only the height its rows need (up to 70% of the column, then it scrolls inside). Ready to merge folds to a header button, "Ready to merge · N" (N counts its open PRs including other repos' groups), closed by default and remembered per browser. It sits directly under the last Needs you row and opens downward into the space left, scrolling inside. To do cards in the modal have the same reply box as questions (an answer with `replyTo` the card id) and show the last reply; the Ready modal has one too (`replyTo` "pr-N", `pr` N). The cards are "Question" cards (open `question` lines) and "To do" cards (open `todo` lines). Compact and scannable: tag, about chip, time; the `title` in bold (or the text's first sentence); the `text` as one or two sentences of why; `steps` as a numbered list with indented sub-bullets; then option buttons and a reply box, or a Done button. "Nothing needs you." when empty; when not, the header shows a count. One compact card at a time, with ‹ "N of M" › in the header: kind chip (Question / To do), lane chip, PR link, tag chips and the whole title, wrapped; no text or steps. Order: `urgent` tagged cards, then `blocking`, then the rest; newest first within each. The shown card is tracked by id, so an answered or Done card is replaced by the next one, and a card that was not there on the previous render (a new one) becomes the shown card wherever it sorts, with a short glow (none with reduced motion). The first render after loading or switching project does not count as new. Clicking the card opens a modal with the full card (text, steps, options and reply box, or Done), which closes once that card is answered or done. Tags: an optional `tags` array on any line, shown as small chips, `urgent` red and `blocking` orange; `after:"merge"` to dos get a derived "after merge" chip. The panel never shrinks for Ready to merge (flex none, up to 45% of the column, then it scrolls). Chat replies render a `title` (bold) and `steps` like cards do, with or without `text`. Answered and settled cards fold into "Recently done". SQL: a line may carry `sql`, a list of `{title, query, expect}`. The modal shows one query at a time: "N of M: title" (a leading "N of M:" already in the title is not repeated), the query in a monospace block with light SQL highlighting and its whitespace kept exactly (scrolls sideways rather than wrapping), a Copy button that copies the query text unchanged, then "Expect: ...". ‹ "N / M" › buttons and the Left/Right keys (not while typing in a box) flip between queries; the position is kept per card while the page is open. The modal widens to the widest line of any of the card's queries (so flipping does not jump), at least 600px and at most the viewport less 48px; only past that does the block scroll sideways. A click on the backdrop closes the modal (only when the press also started there, so selecting text and letting go outside does not), as do Escape and Close. Steps the writer already numbered ("1. ...") lose that number so they do not show twice. The Sessions column never grows past its 300px: cards are one minmax(0, 1fr) column and long states and models wrap.
  - A question is answered once an answer with its `replyTo` exists, and settled once a `done` line with its `replyTo` exists.
  - A to do with `"after":"merge"` appears once its PR is merged; until then it shows in that PR's Ready to merge window, under "Check on staging after merging". It stays until Done is pressed (`{"replyTo":"<id>","done":true}`) or a `done` line arrives.
- **Ready to merge**: one row per unmerged PR, in exactly the latest `merge-order` line's order and keeping its numbers, with the PR number (linking to GitHub), its plain name from the merge order's `labels` (else the short GitHub title), owning lane (the lane whose `ready` line it was, never the Coordinator), and CI and review score only when GitHub answered. Only merge-order PRs are listed; lane-reported `ready` PRs outside the order are not shown. "Nothing to merge" when the order is empty (or "...yet" when no merge order exists). The header reads "Ready to merge (N)". The merge-order `note` is not shown. To dos whose `pr` is on this list are not shown in Needs you (they would repeat the row); the row shows "N to do" for the ones before merging, and its modal lists them. Another repo: a Coordinator `merge-order` line with `repo` ("owner/name") and an optional `close` list is that repo's merge order, shown under the main list as its own small group (repo name and count, then its open PRs in order with CI, then the `close` PRs marked "Close, do not merge"); each row links to the PR on GitHub. Those PR numbers are looked up in that repo with the same batched query, kept apart from the project's own numbers, and never added to the main list. Clicking a row opens the same modal, which shows only plain words: what it does (the Coordinator's latest `ready` line for the PR), "Before you merge" (its open to dos without `after`), "Check on staging after merging" (its `after:"merge"` to dos, with steps) and the GitHub link.

**Centre: the chat** with the Coordinator only: the person's messages (from the page, and `from:<person>` lines mirrored from the terminal, tagged "terminal") and the Coordinator's lines to the person. Sorted by `ts`, newest at the bottom, auto-scrolling unless the person has scrolled up. `question`, `todo`, `done` and `merge-order` lines are never chat rows, and Done presses are not shown. The person's latest message is highlighted and pinned at the top until a Coordinator line has `replyTo` = its id, or the Coordinator writes to the person after it. Input pinned at the bottom of the column.

**Right (about 300px)**: one compact session card per session, the Coordinator first, then the lanes in order (lane-a, lane-b, ...), (dot, name, `Now` line, open PR count; click for a drawer with the full status file, its PRs with live state, and its messages). A lane board with a `State` field sets the look: Working (green, "Working, ~N min left" from `ETA`, plus time since `Started`), Needs decision (orange card with the question and "Blocked in ~N h"), Blocked (orange card with the `Blocked on` line, only when `State` says so), Handing off or Stopped (red card, "Needs restart: click its VS Code profile"), Done for today (quiet grey card, no restart line, never "stale"), any other value shown as written (grey); clicking it expands Now, Started, ETA, open PRs and Done today with durations, with a link to the drawer. Boards without `State` fall back: "Blocked" (red) when `Blocked on` isn't none; "Waiting on you" (blue) only when an open question has `about` = that session; otherwise "Working" (green); clicking opens the drawer. A board over 15 minutes old gets a grey "stale" chip and fades, except a red restart card. Below the cards, a small **Activity log** link opens a drawer with every lane update, newest first, two lines each, click to expand. Hidden by default: the chat, cards and session cards cover it day to day.

**Menu** (top right): `plan.md`, `rules.md`, `coordinator-rules.md`, read-only. **Project switcher** in the top bar when more than one project is configured.

## Replying
- Every reply box takes typing, has a mic button that dictates live into the box (Web Speech API; hidden where unsupported), and takes pasted (Ctrl+V) or dropped images with thumbnails and a remove button before sending.
- Enter sends, Shift+Enter adds a new line.
- Option buttons fill the reply; the person can add words, then send. The line gets `choice`.
- Everything goes to the Coordinator.
- Images are saved as `<lanesFolder>/attachments/<answer id>-<n>.png` (other formats converted to PNG in the browser), never overwriting, and listed by full path in `attachments`.

## PR state
From the `gh` CLI, run read-only in the project's repo folder (gh finds the repo from its remote): one batched GraphQL query per refresh, 25 PRs per query, for title, state, body, checks and unresolved review threads. GitHub allows 5,000 GraphQL points an hour per account, shared with the lanes pushing as the same account, so a merged or closed PR is never asked about again, and a failed lookup keeps the last good answer. Shown: CI (pass, pending, fail; a check that ran more than once on the commit counts only by its latest run, and a cancelled run is neutral, never a fail), the review score (`Confidence Score: N/5` in the PR body), open threads, merged or open; nothing when GitHub has not answered. A failure (for example the rate limit) shows once, as one line under Ready to merge. Refreshed every 60 seconds and on Refresh.

## Look and feel
Clean and calm. Lots of space, one accent colour, a small fixed type scale (12, 14, 16, 20). Light and dark, following the system. Each session has one colour, used only as a small marker. No em dashes in any text the page shows (they are replaced in text read from files). Updates appear live without a reload (file watching plus server-sent events).

## How it runs
- `npm install`, then `npm start`; it prints a localhost URL. Listens on 127.0.0.1 only and refuses other Host and Origin headers.
- Config in `config.json` (see the README); `npm run demo` runs on made-up data.
- A Node server with one dependency (`marked`) and a plain HTML, CSS and JS front end.
- Windows first (paths, PowerShell, `gh` on PATH), with nothing Windows-only in the code.
